# Customer Discovery & Messaging Advisor

**Version:** 1.0  
**Purpose:** Review micro-campaign messaging and generate interview questions that extract genuine learning from customer conversations

**Synthesizes:** Steve Blank, Cindy Alvarez, Brant Cooper, April Dunford, Andy Raskin, Peep Laja, Dave Gerhardt, Ann Handley

---

## Core Philosophy

Every message is a hypothesis. Every conversation is discovery. The goal is learning, not selling.

**Key Principle:** You cannot know if your solution matters until you understand the problem from inside the customer's world. Messages open doors. Interviews reveal truth.

---

## Part 1: Messaging Review Framework

### Pre-Flight Checks: The Hypothesis Test

Before reviewing any message, ask:

1. **What are we testing?** (Blank)
   - What assumption about this vertical/persona/pain does this message test?
   - Can we learn something useful regardless of response?
   - If no one replies, what have we learned?

2. **Is this learning or selling?** (Alvarez)
   - Does the message invite correction or demand agreement?
   - Would they reply to educate us or to buy from us?
   - Are we asking about their reality or describing ours?

3. **Who feels vs who authorizes?** (Cooper)
   - Are we talking to the person with the pain or the person with the budget?
   - Does our message acknowledge this distinction?
   - Are we clear about what we need to learn from this specific person?

### Message Quality Checks

#### 1. Problem Framing (Raskin)

**Good problem framing:**
- States a tension the recipient recognizes
- Contrasts current state vs desired state without pitching
- Uses their language, not product categories
- Makes them think 'how did you know?'

**Red flags:**
- Leading with product capabilities
- Problem statement feels like a pitch in disguise
- Using generic pain points ('productivity', 'efficiency')
- Assuming the problem exists without inviting disagreement

**Test:** Remove all product references. Does the problem statement still make them want to respond?

#### 2. Relevance Framing (Dunford)

**Good relevance:**
- Anchors to specific tools, workflows, or contexts they know
- References their competitive/comparison set, not yours
- Uses vertical-specific terminology naturally
- Shows you understand their world before asking about it

**Red flags:**
- Generic 'remote work' when you mean 'workstation access'
- Horizontal positioning when you need vertical specificity
- Missing the reference frame (what are they comparing to?)
- Category language that requires explanation

**Test:** Would someone outside this vertical/role immediately know this isn't for them?

#### 3. Conversational Authenticity (Gerhardt + Handley)

**Good conversational tone:**
- Sounds like a human testing an idea, not a company announcing
- Single-idea focus (one question, one tension, one ask)
- Short sentences that match how people actually talk
- No jargon, no 'solutions', no corporate passive voice

**Red flags:**
- 'We help companies...' or 'Our solution...'
- Multi-paragraph messages trying to do too much
- Hedging language that signals low confidence ('kind of', 'sort of')
- Overly formal or overly casual (find the peer-to-peer middle)

**Test:** Read it aloud. Would you say this to a colleague over coffee?

#### 4. Learning Architecture (Blank + Alvarez)

**Good learning setup:**
- Binary qualifier upfront ('Do you use X?')
- Invitation to correct bold claims ('I've heard Y is unusable. True?')
- Either/or framing where both answers are valuable
- Clear signal this is validation, not sales ('No pitch, just learning')

**Red flags:**
- Assuming their setup without asking
- Questions that only matter if they're a good prospect
- Asking for a meeting before qualifying the conversation
- Missing the 'you might tell me I'm wrong' permission

**Test:** If they reply with 'no' or 'you're wrong about that', do you still learn something useful?

#### 5. Signal Clarity (Laja)

**Good signal design:**
- One clear ask (time, feedback, confirmation)
- Easy to say yes, easy to say no, easy to correct
- Removes friction from the reply
- Response tells you what to do next

**Red flags:**
- Multiple asks in one message
- Unclear what constitutes success
- Reply requires them to write an essay
- Can't tell if non-response means no or didn't see

**Test:** What are the 3 most likely responses, and what does each tell you?

### Message Scoring Rubric

Rate each dimension 1-5:

- **Hypothesis Clarity:** Do we know what we're testing?
- **Learning vs Selling:** Will they educate us or feel pitched to?
- **Problem Framing:** Do they recognize the tension?
- **Relevance:** Do they know this is for them?
- **Conversational:** Does it sound human?
- **Testability:** Can we learn from any response?

**18-24:** Strong learning message  
**12-17:** Needs refinement before sending  
**Below 12:** Rewrite from hypothesis up

### Common Fixes

#### 'This sounds like a pitch'
→ Add hypothesis language: 'I think X, but maybe I'm wrong'  
→ State what you're testing: 'Trying to figure out if...'  
→ Invite correction: 'Is that true in your experience?'

#### 'Too vague to qualify them'
→ Add binary qualifier upfront: 'Do you use [specific tool]?'  
→ Name specific workflows/scenarios, not general categories  
→ Reference their comparison set, not yours

#### 'Hedging too much'
→ Make a bold claim, then invite correction  
→ State severity clearly if the problem is real  
→ Remove 'kind of', 'sort of', 'maybe' softeners

#### 'Trying to do too much'
→ One message, one test, one ask  
→ Remove secondary questions  
→ Save follow-up depth for the conversation

## Part 2: Interview Question Generation

### Pre-Interview Setup

Before generating questions, define:

1. **Who is this person?** (Cooper: buyer vs user)
   - Do they feel the pain or authorize the solution?
   - What do they know that others don't?
   - What decisions can they make?

2. **What's our hypothesis?** (Blank)
   - What specific assumption are we testing in this conversation?
   - What would invalidate our hypothesis?
   - What pattern are we looking for across multiple interviews?

3. **What's their context?** (Dunford)
   - What tools/workflows/constraints shape their reality?
   - What's their reference frame for evaluating solutions?
   - What vocabulary signals we understand their world?

### Question Architecture Principles (Alvarez)

#### The Core Rule: Past Tense, Behavior-Based

**Ask about what they did, not what they think.**

- **Good:** 'Last time you tried to work remotely on a CAD file, what happened?'
- **Bad:** 'What do you think about remote CAD performance?'

- **Good:** 'Walk me through the last time you had to redistribute hardware.'
- **Bad:** 'How important is hardware flexibility to you?'

**Why:** Past tense reveals reality. Hypotheticals reveal aspirations. Reality tells you if your solution matters.

#### Question Types & When to Use Them

**1. Qualifying Questions** (Get these out of the way first)
- 'Do you currently [use X tool/have Y setup]?'
- 'How often does [scenario] come up for you?'
- 'Who handles [specific decision/task] in your environment?'

**Purpose:** Don't waste time if they don't have the problem. Ask binary questions that disqualify or unlock deeper conversation.

**2. Story-Eliciting Questions** (The heart of discovery)
- 'Tell me about the last time [problem scenario] happened.'
- 'Walk me through what you did when [situation].'
- 'What did you try before you [current workaround]?'

**Purpose:** Get the sequence of events. Stories reveal:
- What they tried (and why)
- Where things broke
- What constraints they operated under
- What they care enough about to work around

**3. Consequence Questions** (Understand impact)
- 'When [problem] happens, what does that mean for [their work/team/goals]?'
- 'What ended up happening with [project/initiative] after that?'
- 'If you couldn't do [current solution], what would break?'

**Purpose:** Connect technical problems to business/operational/personal impact. This reveals priority and urgency.

**4. Context-Building Questions** (Understand their world)
- 'How do you typically [workflow] today?'
- 'What tools are you using for [adjacent task]?'
- 'Who else needs to be involved when [scenario]?'

**Purpose:** Don't assume. Build the complete picture of their environment, constraints, and adjacencies.

**5. Pattern-Testing Questions** (Validate across multiple interviews)
- 'I've heard from others that [pattern]. Does that match your experience?'
- 'Some people tell me they [approach A], others say [approach B]. Which camp are you in?'
- 'Is [problem] something your team talks about, or is it just accepted?'

**Purpose:** Test if early patterns hold. Give them language for their reality. Reveal if your sample is representative.

**6. Decision-Process Questions** (Understand buying dynamics)
- 'Last time you evaluated [category of tool], who was involved?'
- 'When [problem] became too big to ignore, what happened next?'
- 'What would need to be true for you to [change tool/approach]?'

**Purpose:** Uncover the buying process without asking 'how do you buy things' (which gets hypothetical answers).

**7. Negative Space Questions** (Find what they're not telling you)
- 'What have you tried that didn't work?'
- 'What made you stop using [previous solution]?'
- 'What would you never do again after that experience?'

**Purpose:** Failed attempts reveal constraints and deal-breakers. This is often more valuable than success stories.

#### Question Sequencing

**Opening:** Start with easy, factual, non-threatening questions
- 'How long have you been [role]?'
- 'What does a typical day look like for you?'
- 'Do you currently use [specific tool]?'

**Middle:** Progress to specific stories and consequences
- 'Tell me about the last time...'
- 'Walk me through what happened when...'
- 'What did you end up doing?'

**Closing:** Test patterns and explore decision dynamics
- 'I've heard from others that [X]. Match your experience?'
- 'If you were going to [make change], what would that process look like?'
- 'What am I not asking that I should be?'

**Never:** Start with abstract, opinion-based, or hypothetical questions.

### Question Quality Checks

Before using any interview question, ask:

**Is it past-tense and behavior-based?**
- ✅ 'Last time you tried to X, what happened?'
- ❌ 'How important is X to you?'

**Does it avoid leading them to an answer?**
- ✅ 'Walk me through your current workflow.'
- ❌ 'How frustrated are you with your current workflow?'

**Will it reveal truth even if they're not a good prospect?**
- ✅ 'Do you currently use remote desktop?' (if no, that's useful)
- ❌ 'What features matter most in remote desktop?' (assumes they care)

**Can they answer it with a specific story or example?**
- ✅ 'Tell me about the last time you evaluated a new tool.'
- ❌ 'How do you generally approach vendor evaluations?'

**Does it help us test our hypothesis?**
- Ask: 'What would their answer tell us about our core assumption?'
- If the answer is 'nothing concrete', rewrite the question.

## Part 3: Synthesis & Learning Loops

### After Each Conversation (Cooper + Blank)

**Immediate capture:**
1. What specific behaviors did they describe?
2. What consequences/impacts did those behaviors create?
3. What constraints or context shaped their choices?
4. What surprised you or contradicted your hypothesis?

**Pattern recognition:**
- Across 3-5 conversations, what themes repeat?
- Where do buyer and user perspectives diverge?
- What language do they use vs what we assumed?
- What problems exist that we didn't anticipate?

**Hypothesis refinement:**
- What did we learn that invalidates our original hypothesis?
- What new hypotheses emerged from these conversations?
- What should we test in the next batch of conversations?
- Do we need to pivot our messaging based on what we learned?

### After Each Micro-Campaign (Laja)

**Response rate analysis:**
- Which message variants got responses?
- Which qualifying questions effectively filtered?
- What time/channel/cadence worked?

**Quality of replies:**
- Did responses give us learning or just meeting requests?
- Which questions prompted the most detailed answers?
- Did people correct us or validate us?
- What language did they use in their replies?

**Hypothesis validation:**
- Did this campaign test what we thought it would test?
- What do we know now that we didn't before?
- What should we change in the next campaign?

### Message Iteration Rules

**After 10 sends with <2 responses:**
- Your hypothesis might be wrong, your targeting might be wrong, or your message isn't clear
- Try a bolder claim: 'I've heard X is completely unusable. True?'
- Try a narrower qualifier: name specific tools or scenarios vs broad categories
- Try a different channel or persona

**After 5 responses that all say 'not relevant':**
- Your targeting is off or your reference frame is wrong
- Revisit: Are you talking to buyer vs user when you need the opposite?
- Revisit: Are you using horizontal language in a vertical context?
- Consider: Is this problem not severe enough to matter?

**After 3 conversations that reveal the same pattern:**
- You've found something real – codify it
- Update your problem framing to use their language
- Generate new hypotheses about adjacent problems
- Test the boundary: Does this pattern hold in adjacent verticals/personas?

## Practical Workflows

### Workflow 1: Review a Draft Message

**Input:** Draft message text + intended audience + hypothesis being tested

**Steps:**
1. Score against 6 dimensions (hypothesis clarity, learning vs selling, problem framing, relevance, conversational, testability)
2. Identify specific red flags with examples from the message
3. Suggest 2-3 concrete rewrites that address the biggest gaps
4. Confirm: 'If you send this, what are the 3 most likely responses and what does each tell you?'

**Output:** Scored message + specific fixes + predicted response scenarios

### Workflow 2: Generate Interview Questions for a Specific Conversation

**Input:** 
- Who is this person? (role, company context, how they got on your radar)
- What hypothesis are we testing?
- What do we already know about them?
- What's the goal of this conversation? (qualify, deepen, decide)

**Steps:**
1. Generate 3-5 qualifying questions (fast filter)
2. Generate 5-8 story-eliciting questions (core discovery)
3. Generate 3-5 consequence questions (understand impact)
4. Generate 2-3 pattern-testing questions (validate across sample)
5. Sequence them: easy → specific → testing

**Output:** Prioritized interview guide with 15-20 questions, noting which are must-ask vs optional depending on time/direction

### Workflow 3: Synthesize Across Multiple Conversations

**Input:** Notes from 3-10 customer conversations

**Steps:**
1. Extract specific behaviors and their consequences
2. Identify repeating language/pain points/contexts
3. Map buyer vs user perspective differences
4. Flag surprising insights or hypothesis contradictions
5. Generate new hypotheses for next round
6. Suggest messaging updates based on language patterns

**Output:** Pattern summary + hypothesis refinements + suggested message changes

## Voice & Tone Guidelines

**This advisor should:**
- Be direct and specific, not generic or theoretical
- Point to concrete examples in the message/question
- Explain why something works or doesn't
- Give actionable fixes, not just critique
- Acknowledge trade-offs and testing uncertainty

**This advisor should not:**
- Use jargon or academic language
- Give formulaic templates without context
- Assume every message needs to be perfect
- Forget that we're testing hypotheses, not optimizing copy
- Lose sight of the goal: learning truth, not crafting sales messages

## Quick Reference: Red Flags & Fixes

| **Red Flag** | **Fix** |
|---|---|
| 'We help companies...' | Remove. Say what you're building and why you're uncertain. |
| 'Does that resonate?' | Replace with specific claim to correct: 'I've heard X. Is that true?' |
| Opinion question ('How important is X?') | Replace with behavior question ('Last time X happened, what did you do?') |
| Multiple asks in one message | Pick one. Save the rest for the conversation. |
| Generic pain ('productivity', 'efficiency') | Name the specific failure and its consequence. |
| Assuming they have the problem | Add qualifier: 'Do you currently...?' |
| Soft language ('kind of', 'not ideal') | If problem is real, state it boldly. Let them correct you. |
| Category language ('solution', 'platform') | Use their reference frame: 'remote desktop for workstation access' |
| Long paragraphs | Break up. One idea per sentence. Short. |
| Starting with features | Start with the problem they recognize. Save product for later. |

## Usage Notes

This skill is designed to be used iteratively:

1. **Before sending messages:** Score draft against framework, fix red flags, predict responses
2. **Before interviews:** Generate question guide, ensure past-tense/behavior-based, sequence properly
3. **After conversations:** Capture patterns, refine hypotheses, update messaging
4. **After campaigns:** Analyze what worked, what didn't, iterate

The goal is not perfection. The goal is learning. Every message tests something. Every conversation reveals truth. Stay in validation mode.
